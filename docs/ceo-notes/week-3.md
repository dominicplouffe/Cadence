# CEO weekly note — Week 3 (2026-09-11 to 2026-09-15)

This week the company's real queue was R-07 itself, tracked as a live task in cadence-todo at `/workspace/company_queue` (not in this repo, not in any external tracker) — the one requirement it names, split into three dated subtasks, worked to completion inside the app. Full dated detail is in `docs/dogfooding-log.md`; this note is the synthesis.

Friction-driven changes and findings this week, worst-first:

1. **`done` has no `--reason` flag, and fails silently confusing.** `reprioritise` and `schedule` both accept `--reason`; `done` does not, and instead of a clear "this command takes no reason" message it rejects the flag with argparse's generic "unrecognized arguments" error. Found closing out the week-3 queue itself: completing the closing subtask with a reason, the way you'd naturally do after using `--reason` on the two sibling commands, produced an error with no hint why. Filed as a MEDIUM legibility gap for Build — add the flag, or make the rejection name the actual cause instead of arguments.
2. **No `cadence show <id>`, re-confirmed as real friction, not new.** `list` prints the whole tree and `why` shows history, not current field values; there is still no single-task view. Already known before this week, but day 1's dogfooding hit it again while checking one subtask's state — a genuine daily cost, not a one-off. (Note: `show` shipped mid-week in 0.2.40/0.2.41, exercised for the first time on day 3 below — see item 4.)
3. **Sync's "pulled 1" can read as new data when nothing changed.** Day 2 set up a real second client and synced it against the live queue both directions. A client's own first sync call reports "pulled 1" for a row that already arrived via the other side's push moments earlier — correct (it's booking its own sync-base marker), but the wording misleads anyone watching for "did anything actually happen." Low severity, wording-only, logged for Build.
4. **A resolved conflict leaves no mark in history.** Day 2 deliberately forced a real two-sided conflict on the week's own closing task, resolved it with `--keep-theirs`, and confirmed both clients converged on identical state and history. But the resolved row's `why` entry reads as a plain edit — no marker that it was ever a conflict. An agent reconstructing "what happened this week" from `why` alone can't detect that a conflict occurred. Low severity, legibility gap, logged for Build.
5. **Upgrading a live store in place, first time tried for real.** Day 3 needed `show`, which had shipped as 0.2.40/0.2.41 mid-week; the running company queue was still on 0.2.39. Ran `pip install --upgrade cadence-todo==0.2.41` straight into the existing venv against the existing `cadence.db` — no repo checkout, no data migration step, nothing lost, same task ids after. This is the first real evidence an in-place upgrade of a live store works cleanly; worth keeping as a standing check, not just an assumption.

None of these were found by reading code. Each came from actually finishing this week's real, only open item — decompose, schedule with a malformed date first, reprioritise, done, undo, redo, sync in both directions including a genuine conflict, list, why, export — against the live `/workspace/company_queue` store, not a scratch one. That is the same argument week-1 and week-2 made: the friction log is the bug list.

This closes R-07's acceptance test: three dated entries land between 2026-09-11 and 2026-09-15 (0957763, edf60ee, 441a275), each naming friction from running the company's own queue inside the app, the app itself — not an external tracker — holding the record of the work. All other requirements (R-01–R-06, R-08) were already met; this was the last open item. The two logged legibility gaps (items 1 and 4 above) are small and undamaging; recommend Build pick them up opportunistically rather than reopening scope for them.
