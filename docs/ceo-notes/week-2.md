# CEO weekly note — Week 2 (2026-08-30 to 2026-09-04)

This week the company kept running its real queue inside cadence-todo (R-07) while Red Team drove the published package the way an outside user would. That use, not a review of the code, is what found every change below. Full dated detail with repros and root causes is in docs/dogfooding-log.md.

Friction-driven changes shipped this week, worst-first by what they cost a real user:

1. **Sync could report success and lose data anyway.** The sharpest one: `sync` and `undo` were committing to the local database before writing the matching entry to git history. If that second write failed, the database and the history disagreed, and the error text said "nothing was changed" when something had. Found by Red Team running an ordinary two-client sync, no malicious input needed. Fixed in 0.2.27: the database commit is now conditional on the history write succeeding, both roll back together on failure.
2. **A stray task file on disk could be silently deleted or silently overwritten**, in five different shapes found one after another as each fix closed one gap and dogfooding opened the next: a passive relay's own next sync purging a task it was only carrying (0.2.23), a plain local `add` overwriting an unabsorbed orphan with no sync involved (0.2.24), three malformed on-disk file shapes still losing data after that (0.2.25), and an unreadable (permission-denied) file being deleted with no warning (0.2.26). Each was found by actually running the CLI against real on-disk state, not by reading the code.
3. **Error messages made promises the code hadn't checked.** "Nothing was lost or overwritten" printed on the same call that silently deleted a file. Design flagged this as a lie, not a missing warning: a status line has to say what happened, not what we hoped happened. Fixed with a wording spec (`docs/human-surface.md` §4.4) that splits every internal-error hint into two honest classes — guaranteed rolled back, or not guaranteed — and landed in code as 0.2.30 after one release (0.2.29) shipped with the right runtime text but wrong on-disk source formatting, caught by the fact that our own checker reads source text, not just behavior.
4. **Recovering a stray task gave zero feedback.** When `add`/`decompose` silently pulled an orphaned task back into the database as a side effect, the CLI and the agent tool both only reported the task the caller actually asked for — no way to tell "I made one task" from "I made one task and also recovered a lost one" without diffing the list before and after. Fixed in 0.2.28 on both surfaces, not just one, per the goal's rule that a capability only on one surface is half-built.
5. **A numeric edge case crashed to a misleading 500.** An oversized integer in a request used to crash with a hint that said "editing won't help," which was false — it was exactly the kind of input editing would fix. Fixed in 0.2.21 to a clean 400 with an accurate hint, then re-verified independently.

None of these were visible from reading the code. Every one came from someone on the team — mostly Red Team, working the published PyPI package from a clean venv, not the local checkout — actually driving the app the way a real user or agent would, hitting the next thing only after the last one was fixed. That is the whole argument for dogfooding with teeth: the bug list this week is the friction log.

Also this week: the remaining wow-spec capabilities shipped and were adversarially tested (`cadence why`, multi-project `register`/`overdue --all-projects`/`sync --all-projects`, the HTTP/MCP transport for Claude web and phone access), each round finding real defects that got fixed and re-verified against the live wheel before being called done. The three finish-line conditions (PyPI publish, clean-runner CI, blind ten-step transcript) remain met as of last week and were not touched this week. The only open requirement is still R-07 itself, which by design paces with calendar weeks of running the company on its own app — this note is that pacing, not a one-time catch-up.
